# Learn-it clean-generation foundation v1

- Work package: `ARC-WP-022`
- Baseline: `135c7ee2729451e7e796749a38bf250f142c0ed4`
- Contract: `learnit.kit.v2`
- Successor root: `apps/learnit-next/`
- Legacy product: RC718, retained unchanged
- Status: architecture and execution design; no successor implementation in this package

## 1. Product promise of the first slice

The first successor candidate proves one complete and understandable learning loop:

```text
empty library
→ strict v2 package import
→ course visible in the library
→ start one course session
→ answer QCM and fill activities
→ receive explicit feedback
→ persist progress
→ reload and resume
```

It does not attempt to recreate the complete RC718 product. A capability is carried forward only when it is needed to prove this loop.

## 2. Clean-break boundary

RC718 remains the frozen legacy generation. The successor:

- does not import `learnit.import.v1.1`;
- does not read or migrate the RC718 library;
- does not read or migrate sessions, progress, bilans, retention or patches;
- does not reuse RC718 localStorage keys or IndexedDB databases;
- does not clear RC718 data during reset;
- is distributed under a distinct product and artifact identity.

Historical access is provided by RC718 itself, not by a compatibility layer.

## 3. Contract boundary

The sole normative package schema for the first slice is:

`contracts/learnit-kit-v2.schema.json`

The schema deliberately supports only:

- packages containing one or more courses;
- explicit objectives;
- QCM activities;
- fill activities;
- canonical package, course, objective, activity, choice, slot and token identities;
- immutable package, course and activity revision identities and digests.

Media, matching, ordering, classification, flashcards, content patches and advanced retention are outside this foundation.

### 3.1 Identity rules

All canonical identity fields are lowercase UUID version 4 strings generated once and persisted in the authoring source.

They are never regenerated from:

- title or subtitle;
- normalized text;
- filename or directory path;
- array position;
- package order;
- local collision suffix;
- content digest.

Lineage IDs remain stable across semantic revisions. Revision IDs change when the corresponding immutable semantic payload changes.

Local installation IDs are generated by the Player at successful import and never appear in the authored package:

- `packageInstallId` identifies one local package installation;
- `courseInstallId` identifies one locally installed course.

Display labels may change locally without changing canonical or installation identity.

### 3.2 Canonical digest rules

Digest input uses a deliberately small canonical JSON profile:

1. UTF-8 encoding;
2. Unicode strings normalized to NFC;
3. object keys sorted lexicographically by Unicode code point;
4. arrays retain authored order;
5. no insignificant whitespace;
6. values limited to objects, arrays, strings, integers, booleans and null;
7. the digest field of the object being digested is omitted;
8. digest representation is `sha256:<64 lowercase hexadecimal characters>`.

Digest levels are evaluated inside out:

1. each activity revision digest;
2. each course revision digest, including its activities and their declared digests;
3. the package revision digest, including all courses and their declared digests.

The semantic validator rejects:

- duplicate IDs in the relevant scope;
- missing objective, choice, slot or token references;
- a correct QCM choice not present in `choices`;
- duplicate fill slot answers;
- token usage exceeding `maxUses`;
- the same revision ID with a different digest;
- a declared digest that differs from the calculated canonical digest.

## 4. Activity semantics

### 4.1 QCM

Answers reference `choiceId`, never an array index. Reordering choices therefore does not silently change answer semantics.

A QCM is complete when one declared choice is selected. Correctness compares the selected `choiceId` with `correctChoiceId`.

### 4.2 Fill

The rendered sentence is an ordered `segments` array containing explicit text and slot objects. Every blank therefore has an authored position and a stable `slotId`.

Tokens have explicit `tokenId` and `maxUses`. The same token may fill several slots only when its declared maximum allows it. This prevents the RC718-era ambiguity where a required reusable label could become unavailable after its first use.

A fill activity is complete when every declared slot has one token assignment. Correctness compares the slot-to-token mapping with `answers`.

## 5. Storage architecture

The successor uses:

- localStorage prefix: `learnit.next.v1.`;
- initial localStorage key: `learnit.next.v1.ui` for non-authoritative UI preferences only;
- IndexedDB database: `learnit_next_v1`;
- database version: 1.

The IndexedDB stores are:

| Store | Key | Owner | Purpose |
|---|---|---|---|
| `packages` | `packageInstallId` | import/library | validated immutable package plus local display label |
| `courses` | `courseInstallId` | library | installed-course projection and package reference |
| `progress` | `[courseInstallId, activityRevisionId]` | progress | attempts, correctness, completion and last-updated time |
| `meta` | `key` | application | schema version, active course and bounded recovery metadata |

The first slice does not use localStorage as a duplicate authoritative state cache.

### 5.1 Protected RC718 storage

Successor code must not access these RC718 localStorage keys:

- `learnit_clean_state_v2`;
- `learnit_imported_courses_v1`;
- `learnit_import_history_v1`;
- `learnit_import_last_applied_v1`;
- `learnit_import_transaction_v1`;
- `learnit_active_course_v1`;
- `learnit_content_patches_v2`;
- `learnit_library_revision_v1`;
- `learnit_library_persistence_meta_v1`.

It must not open, delete or upgrade the RC718 IndexedDB database:

- `learnit_durable_library_v1`.

A browser test snapshots all protected values and database contents before successor boot, import, session, reset and close. The bytes and records must be unchanged afterward.

## 6. Import transaction

Import follows a single fail-closed sequence:

1. parse JSON without writing;
2. verify exact contract discriminator;
3. validate JSON Schema shape;
4. run semantic identity and reference checks;
5. calculate and compare revision digests;
6. build an in-memory installation plan;
7. allocate local installation UUIDs;
8. commit package, courses and initial metadata in one IndexedDB transaction;
9. publish the new library projection only after transaction completion.

Any failure before step 8 writes nothing. Any transaction failure aborts the full import.

Legacy packages fail at step 2 with a clear contract-version message.

## 7. Session and progress

The first session queue follows authored activity order. It does not implement adaptation, spaced repetition or diagnostic branching.

For each attempt, progress records:

- `courseInstallId`;
- `activityLineageId`;
- `activityRevisionId`;
- attempt count;
- last answer in the bounded activity-specific representation;
- latest correctness;
- completion flag;
- ISO timestamp generated at the write boundary.

The first slice displays completed/total activity count. It does not claim mastery, retention or long-term learning effectiveness.

## 8. Build and release discipline

The successor uses a deterministic Python-standard-library build. It produces one self-contained file:

`apps/learnit-next/dist/learnit-next.html`

Build rules:

- source order comes only from `source_manifest.json`;
- no generated timestamp, random identifier or environment path enters the artifact;
- a clean build runs twice and produces the same SHA-256;
- the artifact tested by browser suites is the artifact proposed for human evaluation;
- generated `dist/` content is never committed.

## 9. Golden-kit scope

Two foundation kits are required:

- Nombres complexes;
- Signaux électriques.

Each contains at least:

- one course;
- two explicit objectives;
- six activities;
- at least three QCM activities;
- at least two fill activities;
- one application or transfer activity;
- one validation activity.

These are representative foundation fixtures, not yet complete release curricula. Their purpose is to exercise authentic mathematical and physical-science content through the entire product slice.

## 10. Acceptance matrix

The first integrated candidate must prove:

1. empty first launch;
2. deterministic import of each v2 golden kit;
3. atomic rejection of a legacy package;
4. atomic rejection of malformed references and digest mismatches;
5. homonymous course titles with different canonical IDs can coexist;
6. local display-label editing does not change canonical IDs;
7. QCM answer correctness is stable when choices are reordered;
8. fill token reuse obeys `maxUses`;
9. progress persists through refresh and browser restart;
10. resetting successor data does not modify RC718 data;
11. opening and using the successor does not modify RC718 data;
12. clean builds are deterministic;
13. tested artifact equals proposed artifact;
14. working-file count does not exceed 32;
15. no held platform domain is introduced.

## 11. Human gate

The first successor candidate requires a distinct human gate. The test notice must state explicitly:

- this is a new generation, not an RC718 upgrade;
- RC718 library and learning history are not imported;
- RC718 remains separately available;
- only the bounded foundation loop is under evaluation.

## 12. Deferred capabilities

The following require later work packages after the foundation loop is accepted:

- additional activity families;
- media and jacket assets;
- advanced library organization;
- adaptive sequencing;
- bilan and explainable mastery;
- spaced review and retention;
- import/export beyond v2 package import;
- content patches;
- performance scale beyond the golden fixtures;
- backend, accounts, synchronization, catalog, commerce, tenancy and marketplace.
