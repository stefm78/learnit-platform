# ADR-0002 — Clean-break Learn-it generation

- Status: **Accepted with conditions**
- Work package: `ARC-WP-021`
- Decision date: 2026-07-15
- Reviewed baseline: `0575385c5891e56506de6aaa0244297d766ea458`
- Legacy product preserved: **RC718**, RC719 `PASS_WITH_RESERVATIONS`
- Implementation status: **not yet authorized**

## 1. Decision

Learn-it adopts trajectory **C — clean break**.

The next product generation will not provide automatic compatibility or migration for RC718 local data or content contracts. It will start with:

- a new major content contract;
- canonical identity from creation;
- a distinct storage namespace and durable database identity;
- an empty learner state;
- regenerated or explicitly converted kits;
- its own source, build, test, artifact and promotion evidence.

RC718 remains a frozen, retrievable legacy standalone product. It is not upgraded in place.

## 2. Relationship to ADR-0001

`ADR-0001-STABLE-IDENTITY-MIGRATION.md` established two things:

1. an identity taxonomy separating canonical lineage, local installation identity and legacy compatibility keys;
2. a continuity strategy based on resolver, overlay, transactional migration and mixed-version operation.

This decision keeps the identity taxonomy and its prohibition against title-derived canonical IDs.

This decision **supersedes the continuity strategy**. The following work is cancelled unless a future accountable-owner decision explicitly reopens it:

- read-only compatibility resolver for RC718 payloads;
- identity overlay over existing RC718 data;
- migration of RC718 learner-state maps;
- dual read or dual write between legacy and canonical keys;
- mixed legacy/canonical library support;
- legacy import-contract compatibility in the new generation;
- contract-v1-to-v2 transparent cutover.

## 3. Why the rupture is accepted

### Evidence

- RC718 is a validated standalone baseline and can remain available independently.
- The current product has no deployed account, backend, synchronization, remote catalog, institutional tenancy or marketplace obligation.
- The expensive continuity path exists mainly to preserve local library and learner-state structures keyed by legacy course and activity identifiers.
- The Player is already at its enforced working-file ceiling of 150 files.
- The current identity taxonomy is useful for a new generation even when legacy data is not migrated.

### Accountable-owner decision

The accountable owner explicitly decided that no current justification warrants the development and maintenance cost of continuity and selected trajectory C.

### Assumptions

- Current RC718 local data is development or limited-use data whose loss from the new active product is acceptable.
- Users who require their old state can continue to open the frozen RC718 artifact.
- The authoring pipeline can regenerate priority kits under the new contract.

These assumptions must be revisited before external distribution of the new generation.

### Absence of evidence

There is no evidence of:

- a contractual obligation to preserve RC718 learner history;
- a production population requiring transparent upgrades;
- cross-device or multi-user data whose migration is mandatory;
- a business benefit exceeding the cost and risk of the compatibility layer.

## 4. Explicitly accepted concessions

The new generation will not automatically preserve:

- imported RC718 library contents;
- plan or course display-name customizations;
- active course selection;
- active or completed sessions;
- answers and queues;
- progress by course and activity;
- bilans and review lists;
- retention schedules and history;
- import history and last-applied reports;
- field evidence or content-patch references;
- RC718 localStorage or IndexedDB snapshots.

Existing kits using the RC718 contract are not directly supported. They must be regenerated by the aligned authoring skill or passed through an explicit offline converter whose output is validated as a new-generation package. The converter is a content-production tool, not a runtime compatibility layer.

## 5. Legacy preservation boundary

RC718 must remain forensically reproducible and usable as the legacy generation:

- product source commit remains `decd9b77bc77a6de9dc28497d0f3affeb972e964`;
- promoted artifact SHA-256 remains `e6ca9523bfd8fd59a5bf6abbfb1ee1c2f0de46c429c44749354c881eb31ff3eb`;
- human gate remains RC719 `PASS_WITH_RESERVATIONS`;
- accepted architecture and release evidence remain immutable;
- the artifact remains downloadable or reproducible through repository release procedures.

The new generation must not silently mutate, clear, import or reinterpret any RC718 browser storage.

## 6. New-generation boundary

### 6.1 Product identity

The first candidate must use a clearly distinct product generation and release identity. It must not masquerade as a transparent RC718 update.

### 6.2 Content contract

The new contract is a major boundary, not an additive reinterpretation of `learnit.import.v1.1`.

It must define canonical identities for at least:

- package lineage and immutable package version;
- course lineage and immutable course revision;
- objective lineage;
- activity lineage and immutable activity revision;
- asset lineage;
- local plan and course installation identities where needed.

Canonical IDs remain opaque, immutable and independent of titles, ordering, filenames and local collision suffixes.

### 6.3 Storage isolation

The new generation must use:

- new localStorage keys;
- a new IndexedDB database name or version boundary that cannot open RC718 records as active state;
- a new state schema version;
- no fallback read from RC718 keys;
- no automatic deletion of RC718 keys.

A negative test must prove that opening, using and resetting the new generation leaves RC718 storage bytes unchanged.

### 6.4 Initial state

The first launch starts with an empty library and empty learner state, except for explicitly bundled new-generation content.

A user may manually import a regenerated new-generation kit. Importing an RC718 package must fail closed with an understandable contract-version message.

### 6.5 Authoring alignment

The authoring skill and Player contract must evolve atomically enough that the first promoted new-generation Player has at least two representative validated kits:

- Nombres complexes;
- Signaux électriques.

The golden kits must be produced under the same canonical contract accepted by the Player.

## 7. Development sequence

The clean-break path should minimize transient architecture:

1. freeze RC718 and verify its downloadable artifact and evidence;
2. design the exact new major contract and storage namespace;
3. define the minimum Player file plan, respecting or deliberately revising the 150-file budget;
4. update the authoring contract and regenerate golden kits;
5. implement one narrow vertical slice: import, library, one session, progress and persistence under new identities;
6. run contradictory QA, clean-room build and storage-isolation tests;
7. extend remaining accepted RC718 capabilities only when required by the new product scope;
8. promote through a distinct human gate.

The new generation should not copy all RC718 implementation merely because it exists. Each retained capability must have a current product justification.

## 8. Mandatory safeguards

- No Player implementation begins before a bounded implementation work package is accepted.
- No compatibility resolver, dual-key storage or migration code may be added under the clean-break program.
- New-generation reset actions must not clear RC718 storage.
- Legacy packages must be rejected, not partially interpreted.
- The new contract, generated kits, Player validation and release evidence must agree on exact versions and hashes.
- The reviewed source must produce the tested artifact, and the tested artifact must be the distributed artifact.
- Backend, accounts, synchronization, remote catalog, commerce, tenancy and marketplace remain held.

## 9. Rollback

Before implementation, rollback is a single revert of this decision package.

After a new-generation candidate exists, rollback means:

- stop distributing the candidate;
- continue distributing or using frozen RC718;
- revert the bounded candidate source if appropriate.

Rollback does **not** require converting new-generation data into RC718, and no such reverse migration is promised.

## 10. Adversarial acceptance cases for the first implementation

The first new-generation candidate must prove at least:

1. RC718 storage is byte-for-byte unchanged after new-generation boot, use and reset;
2. a legacy package is rejected with no partial library write;
3. a valid new-generation package imports deterministically;
4. canonical IDs do not change after display-label rename;
5. duplicate display labels can coexist when canonical IDs differ;
6. identical immutable revision IDs with different digests are rejected;
7. progress is isolated by new-generation course installation identity;
8. refresh and browser restart preserve only new-generation state;
9. clean-room build is deterministic;
10. published artifact equals tested artifact;
11. regenerated Nombres complexes and Signaux électriques kits pass contract and product flows;
12. no held platform domain is entered.

## 11. Consequences

### Positive

- Removes the most expensive migration, dual-read and mixed-version work.
- Avoids long-lived compatibility branches in a Player already constrained by file count.
- Makes canonical identity native instead of layered over legacy keys.
- Simplifies tests, rollback and future reasoning.
- Allows the new generation to remove unjustified historical implementation debt.

### Negative

- The new generation is not a transparent upgrade.
- Local RC718 libraries and learner histories do not continue automatically.
- Existing kits require regeneration or deliberate conversion.
- Users may need to retain RC718 alongside the new generation for historical access.
- Product communication must make the rupture explicit.

## 12. Next gate

The next mandatory gate is `ARC-WP-022`.

It must be design and authorization for the minimum viable clean-generation foundation, including:

- exact new contract boundary;
- exact storage namespace isolation;
- initial canonical identity rules;
- regenerated golden-kit plan;
- exact Player files and file-budget decision;
- developer, contradictory-QA, integrator and governor scopes;
- automated and human release gates;
- one-revert implementation boundary.

It must not implement backend, accounts, synchronization, catalog, commerce, tenancy or marketplace.
